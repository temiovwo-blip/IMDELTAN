# Internal security review — development drafts through 064

**Scope:** focused self-review of selected migration and deployment controls, not an independent audit, penetration test or production approval. Current repository `main` ends at 063; 064 and this review are local-only drafts. Development still has foundation plus 001–031. A successful dry-run preview lists changes but does not execute or validate them on the service. Public registration remains closed.

## Findings and actions

1. **Defence-in-depth gap in five internal tables — addressed and tested locally.** `app_private.group_invite_lookup_attempts`, `group_invitation_sends`, `direct_conversation_pairs`, `friend_lookup_attempts` and `friend_request_sends` revoked client table grants but had no RLS. `authenticated` has schema usage for one narrowly scoped helper. No proof of an existing client read or write was found: grants were revoked and the schema is intended to remain unexposed. Nevertheless, a future accidental table grant or schema exposure would remove a useful layer of protection. Local migration 064 enables RLS on the five tables without creating permissive policies, and repeats explicit grant revocation. Table owners and bypass roles can still bypass RLS; RLS is not forced because existing owner-executed functions rely on it. Verify actual function/table ownership and Supabase behavior in an isolated service before rollout.
2. **No independent review or real-service signed-in checks — open.** Draft functions and client controls have synthetic SQL/mock coverage, but no real signed-in synthetic-account authorization, API/storage object/signed URL, mobile or penetration test. The new catalog check is evidence only about a simulated local PostgreSQL installation. Public signup and draft features remain closed.
3. **Missing policy and trust decisions — open.** No mandatory policy versions currently published in dev. Real onboarding is intentionally gated; self-declared age is not proof. Do not insert fake legal text into a shared service or silently bypass policy checks. Privacy, moderation, reporting, retention, user disclosures, abuse monitoring and safe incident response need review.
4. **Direct messages are not end-to-end encrypted — open product/privacy gate.** Sender hide is not erasure; safety/reporting records and backups may retain content. Do not present this as encrypted messaging or complete deletion.
5. **Recovery and operational safety — open.** Migration preview is not a restore test. Before applying drafts to any shared environment, decide how to back up, restore or forward-fix, review ownership and privileges, and assess effects on the existing development account. Never apply to old infrastructure or production.
6. **ZIP permission regression — addressed locally.** A source bundle wrote `gradlew` as non-executable and caused two GitHub Android checks to fail. The review-branch fix restored its executable Git mode and all eight PR checks passed. The local bundle generator now records the wrapper as Unix mode 0755 even when the source file is non-executable, with an offline regression test and real ZIP extraction check. This generator change is not yet on GitHub.

## Local catalog guardrail

`tests/sql/private_security_catalog.sql` checks local `app_private` tables have RLS, no client table grants or private-schema policies; checks application SECURITY DEFINER functions for an empty fixed search path and no anonymous EXECUTE; and checks the allowed authenticated private helper is limited to the exact current-user gate signature. It then demonstrates policy-free RLS on a synthetic lookup row even after a temporary SELECT/INSERT grant, rolling all fixture and privilege changes back. It runs only against disposable PostgreSQL in CI. It does not prove function bodies safe, establish service ownership, check every possible PostgreSQL privilege, test real JWTs or storage, or protect privileged owners/bypass roles. The allowlist requires deliberate updates if a reviewed feature changes the intended baseline.

## Priorities before controlled development deployment

- Finish and record fresh local migrations 001–064, workflow tests and concurrency results; review migration 064 and its effect on internal routines.
- Compare repository/main, migration history and intended target immediately before any approved development-only change. Review restoration/forward-fix and avoid real/sensitive data.
- Establish legitimate reviewed policies and dedicated synthetic identities/fixtures through a separately approved workflow, then run selected authenticated and adversarial real-service tests with positive controls. Do not send tokens in chat.
- Test storage objects and signed URLs separately and only with disposable synthetic objects and appropriate authorization; inspect security around privileged service paths.
- Obtain independent security/legal assessment before public launch or handling real payments and sensitive users. Local self-review cannot substitute for it.

## Fresh local result

A fresh disposable PostgreSQL 17 database ran the exact migration sequence through 064 and the entire database CI workflow, including 19 two-session concurrency suites and the new catalog/RLS test: all passed. The temporary database and synthetic roles were removed and the local cluster stopped. The existing function behavior exercised by those suites continued to pass with the new internal-table RLS, but this does not verify ownership or behavior on real Supabase. 70 Python checks passed, including packaging modes; actual UNIX `unzip` extraction preserved the wrapper's executable bit. No remote migrations, accounts, policies or storage objects were changed.

## Read-only development metadata follow-up

On 7 November, the dedicated dev service's current 001–031 schema contained 41 SECURITY DEFINER functions in `public`/`app_private`; all 41 had an empty fixed search path and none granted anonymous execute. All 41 were owned by an RLS-bypass role, so their function bodies and execution grants are critical authorization boundaries; the metadata results do not prove those bodies are safe. The only authenticated-executable `app_private` helper matched the current-user gate signature. All 36 public ordinary/partitioned tables had RLS enabled. The one current private table, `group_invite_lookup_attempts`, had RLS disabled but neither client role held the checked table- or column-level privileges. Its owner was an RLS-bypass role. Local migration 064 covers that table, but is not on GitHub or applied to development; do not infer a demonstrated exposure from the missing defence-in-depth layer.

`scripts/dev_security_metadata_audit.sql` provides a read-only, aggregated catalog check for repeatable review. It cannot determine whether the connection is really the intended project, establish exposure through other roles, inspect function bodies, or replace real JWT/API tests. Operators must verify the target independently. The local catalog guardrail was also extended to check column-level grants, which table-level checks alone can miss.

The updated catalog audit was subsequently executed on a fresh disposable database with the exact migrations through 064: all seven local private tables had RLS, none had the checked client table/column grants, all 113 local SECURITY DEFINER functions had an empty fixed search path and none was executable by anon. Their owners were RLS-bypass roles in the local test, too. The temporary database and roles were removed. 72 Python guardrails passed. These are metadata and simulated-database checks, not real-service penetration testing or guarantees about function bodies.

## No-identity SECURITY DEFINER probe

Added `tests/sql/null_identity_security_probe.sql` to the local database workflow. In a fresh disposable PostgreSQL database through 064, a simulated `authenticated` role with no JWT subject called each of its 101 executable application SECURITY DEFINER routines using non-null synthetic inputs; all 101 returned SQLSTATE 42501. The one allowed private eligibility helper returned false. The probe checks schema access first, rolls every unexpected success back in a subtransaction, rejects unknown argument types and fails on errors other than 42501. A deliberately permissive synthetic canary was detected and then removed; the test DB and synthetic roles were deleted. This does not prove behavior for valid user identities, real JWT signatures, existing-resource combinations, unauthorized writes in every situation, or real Supabase/PostgREST. The existing 19 full-workflow concurrency suites passed in the preceding run, before this new workflow step was added. The new probe itself was tested separately on a fresh schema; it is not yet on GitHub.
